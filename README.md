## What's monitored

Checked regularly: the workflow asks GitHub for a run every 5 minutes, but GitHub runs schedules best-effort and often less often (when it's late, a run checks up to 4 times, 5 minutes apart, to fill the gap). The status page shows the real check rhythm ("checked about every … (last 24 h)"). Each run, GitHup checks each monitor in [`.githup.yml`](.githup.yml):

- **Stuxedo:** [stuxedo.com](https://stuxedo.com), the Stuxedo media CDN, [Stuxedo Status](https://status.stuxedo.com)
  (the landing page), [Stuxedo Web Status](https://status.stuxedo.dev), and the control panel, webmail, website
  builder and support sites
- **Web status:** the **Web status** workflow saves Stuxedo Web Status's overall state to `data/web-status.json`
  on the same best-effort 5-minute schedule (only committing changes), for the badge on status.stuxedo.com's Web Status button
- **Services:** **runn1 runners**, the Stux GitHub Runner Service on runn1 (Germany): up while every
  self-hosted GitHub runner it has set up is online (`runners-ok.txt`, written every minute by Stuxedo/runners)
- **Region websites:** each region's website (uk, ca, es, fi, us and fr .stuxedo.net), served by that region's own
  server
- **Templates:** the Region Page, Instance Page, Soonpage and Maintenancepage on GitHub Pages, their v1 snapshots,
  and the stuxedo.github.io redirect
- **Servers:** each server's instance page (robo1, tiny1 and web1 in the UK, kitt1 in Canada, mixr1 in
  Spain, mixr2 in Finland, down1 in the United States, soci1 in France, runn1 in Germany). The [Stuxedo](https://regionpage.stuxedo.net) and
  [Stux.Cloud](https://regionpage.stux.cloud) region pages read these monitors (by slug) for their
  live server status
- **Certificates:** each server checks daily that every certificate it uses has more than 21
  days left, and publishes `certificates-ok.txt` while it does
- **New servers** are added on their own: the daily **Servers sync** workflow (`.github/workflows/servers-sync.yml`, `scripts/sync-servers.py`) reads the `*.servers.<cc>.stuxedo.net` records from Cloudflare and gives any new server both monitors, released on `test` with a `test` → `main` PR (it never pushes to `main`; the monitors go live when the PR is merged). A country that isn't a region on the region pages yet fails the run; a monitored server with no record is only warned about. It needs the `CLOUDFLARE_DNS_TOKEN` secret (Zone → DNS → Read on stuxedo.net)
- Web hosting has its own status page, [Stuxedo Web Status](https://status.stuxedo.dev), linked under Elsewhere
  and in the footer. [status.stuxedo.com](https://status.stuxedo.com) is the landing page for both (stuxedostatus.com
  redirects there)
- Elsewhere also links [Stux.Group Status](https://status.stux.group) and
  [Stux.Cloud Status](https://status.stux.cloud), which covers Stux.Cloud's websites and pages

The servers, their certificate checks and the Stuxedo site were checked on
[Stux.Group Status](https://status.stux.group) until 9 October 2026; their history came with them
(`data/<slug>/`).

To add a monitor, add it to the right group there (or a new group). A group can also hold `links:` instead of monitors, for sites that should be listed but not checked.

When something goes down, GitHup opens an Issue on this repository (labelled `githup`,
`incident`, `status` and the monitor's slug) and closes it with the downtime when it recovers.
To announce planned maintenance, open an Issue yourself with the `githup` and `incident` labels
(plus the monitor's slug to link it); it shows on the status page.

## How it works

- **`.github/workflows/status.yml`** runs a GitHup `check` on a best-effort 5-minute schedule (with `fill-gaps`, up to 4 checks when the schedule is late) and commits the
  results to `data/` as `github-actions[bot]`. When a status changes, hourly, and on pushes, it
  builds the GitHup status page into `_site` (with `site-dir`), and deploys it with `actions/deploy-pages`.
- **`legal:` in `.githup.yml`** makes GitHup generate the **Boring Legal Stuff** hub at `/legal/`
  with its six sub-pages, a themed `404.html`, a `/sitemap/` page, `sitemap.xml` and `robots.txt`
  (the base URL is `site.url`). Nothing is hand-made, and the footer shows only
  **Powered by GitHup**. This repo's own `CHANGELOG.md` and `VERSION.md` are for this repo only.
- **`data/`** is the monitoring history. Don't edit it by hand.
- **The status table above** is written by GitHup's `readme` mode between the
  `<!-- githup:start -->` and `<!-- githup:end -->` markers. Don't edit inside them.

## Reliable 5-minute checks

GitHub runs scheduled workflows on a best-effort basis, so the 5-minute schedules in `status.yml` and
`web-status.yml` often run hours apart. RUNN1 starts them instead: every 5 minutes, cron runs
`/usr/local/sbin/stuxedo-status-dispatch` ([`scripts/dispatch-checks.sh`](scripts/dispatch-checks.sh)), which asks
GitHub to run each workflow now unless a run is already queued or running. The schedules stay as a backup.

It uses a fine-grained personal access token with access to **Stuxedo/Status only** and one permission,
**Actions: Read and write**, kept on RUNN1 in `/etc/stuxedo-status/dispatch-token` (root only). When the token
expires, make a new one with the same settings and replace the file.

## Local development

```bash
./dev-server.sh                 # or dev-server.bat on Windows; add a port as the last argument
./dev-server.sh --no-dev-mode   # production rendering
./dev-server.sh --lan           # open it from a phone or another device on your network
```

`dev-server` generates 90 days of example data, builds the status page into `.dev/public` with
`DEV_MODE` on, with its legal pages, 404 and sitemap, and serves it at
`http://127.0.0.1:8000`. It uses GitHup from `$GITHUP_PATH`, a sibling `../GitHup` checkout, or
a fresh clone in `.dev/GitHup`. With `--lan` it listens on every interface instead of `127.0.0.1`
only and prints the addresses to open (usually the `192.168.x.x` one).

## Hosting

GitHub Pages, deployed by Actions (**Settings → Pages → Source: GitHub Actions**), with the custom
domain `status.stuxedo.net` set in the Pages settings. DNS: a `CNAME` record for `status` (in the
`stuxedo.net` zone, ahead of its `*` wildcard) pointing at `stuxedo.github.io`. The repository is
public, so the page's live refresh can read `data/summary.json` straight from GitHub.

## Versioning

This project uses [Date Versioning](https://datevers.ing): each release is numbered by its UTC release date as `YY.MM.DD` (for example `26.10.23`), with `-1`, `-2`… for later releases the same day. See [CHANGELOG.md](CHANGELOG.md) for what changed in each release.

Releases are made and tagged on `test`, then go live through two pull requests: `test` into `staging`, then `staging` into `main` (see [CONTRIBUTING.md](CONTRIBUTING.md#branches-and-going-live)).
